# مدل نگاشت محصول به خودرو و زیرسیستم

## مسئله

دسته‌های فعلی عمدتاً برند سازنده‌اند. نام محصول می‌تواند سیگنال اولیه بدهد اما برای اثبات سازگاری کافی نیست. یک محصول نیز ممکن است به چند خودرو و مدل مرتبط باشد؛ بنابراین Vehicle نباید جای Brand را بگیرد.

## مدل داده پیشنهادی

| فیلد | نوع | الزام | نمونه |
|---|---|---|---|
| `vehicle_make` | taxonomy | اجباری برای صفحه خودرو | Mercedes-Benz |
| `vehicle_family` | taxonomy چندمقداری | اجباری | Axor |
| `vehicle_model` | taxonomy چندمقداری | اختیاری تا تأیید | 1843 |
| `system` | taxonomy | اجباری | gearbox |
| `subsystem` | taxonomy | اختیاری | shift-control |
| `manufacturer_brand` | taxonomy فعلی | حفظ شود | Mercedes / Sachs |
| `oem_number` | متای چندمقداری | در صورت وجود | کد مرسدس |
| `supplier_code` | متا | در صورت وجود | کد ASP یا برند |
| `fitment_status` | enum | اجباری | verified / probable / review |
| `evidence_source` | متن/URL داخلی | برای verified اجباری | کاتالوگ، کارشناس یا مرجع معتبر |
| `verified_at` | تاریخ | برای verified اجباری | 2026-09-06 |

## گردش تأیید

1. از عنوان و SKU فقط Candidate ساخته شود.
2. Candidate با کاتالوگ، کد فنی، داده تأمین‌کننده یا کارشناس فنی بازبینی شود.
3. فقط `verified` در صفحه خودرو و Schema سازگاری نمایش داده شود.
4. `probable` در صف بررسی بماند و برای تولید خودکار صفحه استفاده نشود.
5. هر اصلاح منبع یا تاریخ بازبینی را حفظ کند.

## قواعد عدم تخریب

- دسته و برند فعلی حذف یا تغییرنام داده نمی‌شود.
- URL محصول فعلی فقط برای افزودن داده و لینک داخلی استفاده می‌شود.
- نام محصول به‌تنهایی باعث ثبت `verified` نمی‌شود.
- یک محصول مشترک Duplicate نمی‌شود؛ رابطه چندمقداری به خودروها می‌گیرد.
- تغییرات ابتدا روی نمونه محدود اجرا و پس از QA به موجودی توسعه داده می‌شود.

## نمونه کنترل‌شده اولیه

برای Pilot اکسور، ۳۰ محصول از برندها و زیرسیستم‌های مختلف انتخاب شود. معیار قبول Pilot:

- حداقل ۹۰٪ محصولات نمونه با شاهد معتبر تعیین تکلیف شوند.
- هیچ محصول نامرتبط در صفحه اکسور ظاهر نشود.
- فیلتر خودرو، زیرسیستم و برند خروجی پایدار بدهد.
- افزودن taxonomy URL فعلی محصول را تغییر ندهد.
